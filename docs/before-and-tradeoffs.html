⏮️ Before & trade-offs

Every tool replaced something worse — and is itself the wrong tool somewhere. For each big idea: what life was like before, honest merits ✅ / demerits ❌, and where to use it 👍 vs not 👎.

🗄️ Relational (SQL) vs NoSQL — lessons 02, 11

⏮️ Before relational databases (1970s) and before the NoSQL wave (2009)

Records lived in files with app-specific layouts; every program parsed its own format and nobody could ask a new question without new code. Relational databases put the questions into SQL. Then web scale made some teams throw the constraints away for speed — and many later bought them back.

✅ Merits

  • constraints make bad data impossible, not merely unlikely
  • JOINs and transactions answer new questions without new code
  • one mature room (Postgres) serves most apps for years

❌ Demerits

  • schema changes need migrations (lesson 08)
  • JOIN-heavy queries need care at scale
  • horizontal write scaling is hard (lesson 10)

👍 Use when

  • anything with relationships, money, or rules — the default
  • reporting and ad-hoc questions

👎 Think twice when

  • a question the relational shape answers badly: nearest-by-meaning, graph hops, billions of appends
  • 'NoSQL because scale' with no measurement — the classic regret

🧩 Normalise vs denormalise — lesson 05

⏮️ Before normal forms

One big spreadsheet-shaped table: a teacher's phone number copied into 30 rows, updated in 29, and a report that was wrong for a year.

✅ Merits

  • one fact, one place: updates cannot disagree
  • smaller rows, cleaner constraints
  • the schema documents the domain

❌ Demerits

  • more JOINs per screen
  • read-heavy pages may need several queries

👍 Use when

  • the source of truth; anything edited
  • early — it is much easier to denormalise later than the reverse

👎 Think twice when

  • a hot read path where a measured JOIN is the bottleneck — copy the value and own the rule that keeps it true
  • analytics tables that are rebuilt, not edited

🗂️ Indexes — lesson 06

⏮️ Before the card catalogue

Every question read every line. Fine at 5 rows; the 200,000-row attendance table took a full scan per lookup.

✅ Merits

  • SEARCH instead of SCAN: milliseconds to microseconds
  • enforce uniqueness (UNIQUE) as a side effect
  • make ORDER BY and JOIN cheap

❌ Demerits

  • every write updates every index
  • space; and a wrong column order helps nobody
  • the planner may ignore an index on tiny tables

👍 Use when

  • columns you filter, join and sort on; foreign keys
  • after EXPLAIN shows a SCAN on a big table

👎 Think twice when

  • 'index everything' — writes crawl
  • before measuring — a 5-row table needs no catalogue

🔒 Isolation levels — lesson 07

⏮️ Before isolation

Two clerks writing the same register at once produced torn rows; the fix was 'only one program uses the file' — until there were two programs.

✅ Merits

  • read committed: fast, no dirty reads — the sane default
  • serializable: correctness as if one clerk at a time

❌ Demerits

  • stricter levels wait more and deadlock more
  • subtle anomalies (phantoms, lost updates) at the looser levels

👍 Use when

  • money and counters: serializable or explicit locks (SELECT … FOR UPDATE)
  • everything else: read committed + short transactions

👎 Think twice when

  • long transactions holding locks across user think-time
  • assuming your ORM's default is serializable — it almost never is

🏗️ Expand/contract migrations — lesson 08

⏮️ Before versioned migrations

Someone ran ALTER TABLE on the production room by hand on a Friday; nobody could say what the schema was, and rollback meant memory.

✅ Merits

  • schema in git: reviewable, repeatable, rehearsable
  • expand → migrate → contract keeps school open through a rename
  • the logbook (schema_migrations) makes 'what ran where' a query

❌ Demerits

  • discipline: one migration = one change, always reversible or rehearsed
  • backfills on big tables must be batched
  • two code versions run at once for a while

👍 Use when

  • every schema change, no exceptions
  • zero-downtime renames and type changes

👎 Think twice when

  • a one-step rename on a live table — it breaks the old code instantly
  • destructive migrations without a tested backup (lesson 09)

📈 Read replicas vs sharding — lesson 10

⏮️ Before replicas

One machine; when it filled up, the answer was a bigger machine — until there was no bigger machine.

✅ Merits

  • replicas: cheap read scaling and a warm standby
  • sharding: writes and data spread across rooms — the last resort that works

❌ Demerits

  • replication lag: a reader may see the past
  • sharding breaks JOINs and cross-shard transactions; re-sharding is a project

👍 Use when

  • replicas for read-heavy apps and reporting
  • sharding when one primary genuinely cannot hold the writes — after pool, cache, indexes, bigger box

👎 Think twice when

  • reading your own write from a replica (lag surprises)
  • sharding a 50 GB database because a blog said so

☁️ Managed (RDS) vs self-hosted — lessons 09, 10

⏮️ Before managed databases

Every team ran its own Postgres: patching, backups, failover scripts, and one person who knew where the WAL went.

✅ Merits

  • backups, patches, Multi-AZ failover, monitoring — rented
  • replicas and point-in-time restore are checkboxes

❌ Demerits

  • costs more per hour; less knob access
  • lock-in flavours; migration effort later
  • you still own the schema, queries, indexes and drills

👍 Use when

  • most teams, most of the time (AWS school L17)
  • when the one person who knew the WAL leaves

👎 Think twice when

  • exotic extensions or extreme tuning the service forbids
  • a laptop lab — SQLite is free and honest
