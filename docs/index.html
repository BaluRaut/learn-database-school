═══ model ═══
── one fact, one place — the class name lives in ONE row

    (2, '3B')

   💥 duplicate roll_no refused by the schema: UNIQUE constraint failed: students.roll_no

6 🗂️ Indexes

कार्ड कॅटलॉग — B-trees, EXPLAIN, आणि कॅटलॉग तुम्हाला कधी हळू करतो.

⏪ आधी

index शिवाय student 4242 शोधण्यासाठी सर्व 200,000 attendance ओळी वाचाव्या लागतात, प्रत्येक lookup ला 2.4 ms.

💡 काय

index म्हणजे card catalogue, एक B-tree जो keys drawers मध्ये लावतो म्हणजे तुम्ही थेट योग्य row वर पोहोचता.

⚙️ कसे

CREATE INDEX नंतर EXPLAIN SEARCH … USING INDEX दाखवतो: 200,000 ऐवजी 3 steps, O(n) ऐवजी O(log n).

🎯 का

scan table सोबत दुप्पट होतो, तर index वेगवान राहतो, आणि तो तुम्हाला पहाटे 3 वाजताच्या page पासून वाचवू शकतो.

7 🔒 Concurrency & isolation

दोन कारकून, एक नोंदवही — locks, isolation levels, आणि deadlock चा हस्तांदोलन.

⏪ आधी

isolation शिवाय एकाच row वर एकाच वेळी काम करणारे दोन clerks अर्धवट pencil खुणा वाचू शकतात किंवा एकमेकांचे काम पुसू शकतात.

💡 काय

locks आणि isolation levels ठरवतात की एक transaction pencil मध्ये असताना दुसरे काय पाहू आणि बदलू शकते.

⚙️ कसे

Sita चे नाव बदलण्यासाठी clerk 2 row 2 lock करतो; clerk 1 ला जुने नावच दिसते, आणि त्याचा update COMMIT lock सोडेपर्यंत थांबतो.

🎯 का

pencil खुणा खाजगी राहतात, म्हणून वाचणाऱ्यांना फक्त शाई दिसते, आणि deadlock दोन्ही clerks ना कायम अडकवण्याऐवजी पकडला जातो.

🚀 पुढे

clerks काम करत असतानाच खऱ्या खोल्यांचा आकारही बदलतो, हे पुढचा lesson migrations ने हाताळतो.

8 🏗️ Migrations

migrations शिवाय schema बदल production मध्ये हाताने टाइप होतात, आणि कोणत्या database मध्ये कोणते columns आहेत हे कोणाला कळत नाही.

9 🧯 Backups & recovery

आगीपासून सुरक्षित प्रत — RPO, RTO, point-in-time, आणि तुम्ही खरोखर करता ती restore ची रंगीत तालीम.

⏪ आधी

backup शिवाय एक DELETE किंवा इमारतीतील आग data आणि disk दोन्ही कायमचे घेऊन जाते.

💡 काय

backup म्हणजे दुसऱ्या इमारतीतील fireproof copy: रोज रात्रीची पूर्ण copy आणि प्रत्येक बदलाचा सतत चालणारा log (WAL).

⚙️ कसे

10:14 ला Rohan delete होतो; restore 02:00 चा backup परत copy करतो, log 10:13 पर्यंत replay करतो, आणि तो परत येतो.

🎯 का

point-in-time recovery गमावलेल्या कामाचे तास मिनिटांत बदलते, आणि RPO व RTO सांगतात किती नुकसान व downtime चालेल.

🚀 पुढे

तुम्ही खरोखर केलेल्या restore drill नंतरच backup मोजला जातो; पुढे scaling ने record room वाढतो.

10 📈 Scaling

अधिक कारकून, अधिक खोल्या — pools, replicas, caches, partitions, आणि shard कधी करू नये.

⏪ आधी

योजनेशिवाय teams थेट sharding कडे उडी घेतात, जेव्हा हळू query ला फक्त index हवा होता, आणि कायम complexity ची किंमत भरतात.

💡 काय

scaling म्हणजे क्रमाने क्षमता वाढवणे, स्वस्त आधी: queries सुधारा, pool, cache, मोठे machine, replicas, partitions, shards.

⚙️ कसे

एक primary सर्व writes घेतो तर read replicas थोडे मागे राहून readers ना सेवा देतात, आणि pgbouncer connections pool करतो.

🎯 का

index ने सुधारलेली हळू query उजवीकडील प्रत्येक box पेक्षा चांगली आहे, आणि बहुतेक शाळांना shards कधीच लागत नाहीत.

🚀 पुढे

11 🏘️ NoSQL & इतर खोल्या

Document, key-value, columnar, graph, vector — प्रश्नासाठी योग्य खोली निवडणे.

⏪ आधी

प्रत्येक प्रश्न rows मध्ये कोंबल्याने nested records, microsecond lookups आणि अब्जावधी rows चे analytics हळू किंवा अवघड होतात.

💡 काय

NoSQL म्हणजे प्रत्येकी एका प्रश्नासाठी घडवलेल्या इतर खोल्या: document, key-value, columnar, graph आणि vector stores.

⚙️ कसे

MongoDB nested records ठेवतो, Redis एका key चे उत्तर µs मध्ये देतो, BigQuery अब्ज rows जोडतो, Neo4j friends of friends शोधतो.

🎯 का

constraints, JOINs आणि transactions साठी relational हीच default खोली राहते; ती वाईट उत्तर देते त्या प्रश्नासाठीच दुसरी निवडा.

vector खोली VectorDB school कडे नेते, आणि पुढे तुम्ही कोणतीही खोली operations मध्ये वेगवान कशी ठेवायची ते शिकाल.

12 🩺 Performance & operations

⏪ आधी

triage शिवाय app गुपचूप 500 मुलांसाठी 501 trips करते, आणि database कोसळेपर्यंत हळू query लपून राहते.

💡 काय

operations म्हणजे slow-query log आणि plans पाहणे, आणि record room on call जाण्याआधी N+1 सुधारणे.

WHERE lower(name) = 'sita' 812 ms मध्ये scan करतो; WHERE name = 'Sita' आणि CREATE INDEX ON students(name) ला 0.3 ms लागतात.
